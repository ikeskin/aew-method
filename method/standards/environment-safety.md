# Environment Safety — Ask Before Critical Tool Installation

- Inspect required tools and versions read-only once. Reuse installed project-local tools, existing containers and approved remote test services when they satisfy the task; never silently substitute a different database provider.
- Distinguish **required for implementation or acceptance verification** from optional tooling. A missing required SDK, database server, container runtime or other critical dependency is a **decision requiring user input**, not merely a footnote.
- When a required tool is missing, **ask the user for explicit approval before installation (explicit user approval is required)**. Give the exact tool/version, proposed installation method and target (host, project-local, container, or remote), whether privileged commands or a service start are involved, and the tests blocked without it. Offer an existing approved alternative when possible. Group related permissions into one concise question.
- **Pause only the blocked step and await the answer**; do not install, download OS packages, start services, change global SDKs, or run privileged commands while approval is pending. Continue independent, safe implementation if useful, but do not call the entire task complete when critical acceptance verification remains blocked.
- Explicit approval is scoped to the named action and target, not blanket authorization for later installations. Respect sandbox and system permissions; do not bypass them even if the user approves.
- Project-local dependency restoration required by the task may proceed under existing permissions. OS package downloads (`apt download` included), `apt install`, `dpkg`, `dnf`, `brew`, `snap`, global toolchain changes and service management require prior approval.
- For a PostgreSQL-dependent feature, do not treat SQLite or mocked persistence tests as proof of PostgreSQL behavior. If no real PostgreSQL connection is available, ask permission to provision a suitable test instance or request a connection; report integration verification as **blocked pending approval** until executed.
- If approval is denied, use the approved alternatives or explicitly mark verification blocked; do not repeatedly ask or attempt installation anyway.
- Production and remote resource mutations require their own explicit authorization and provider-side permissions.
